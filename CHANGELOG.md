## [1.2.11](https://github.com/totblabs/Multitap/releases/tag/v1.2.11)

This is the server 1.2.11 and the Windows app 1.1.41. The Host 1.1.44 and the Android app 1.1.28 are unchanged. Nothing behaves differently.

- **The Windows app records where the time goes when the graphics card decodes.** It keeps the time to turn a picture into a texture, and the part of it spent waiting for the graphics card to finish. The server stores both with the connection records. They are there to tell why hardware decoding is slow on some PCs.

## [1.2.10](https://github.com/totblabs/Multitap/releases/tag/v1.2.10)

This is the Host 1.1.44 and the Windows app 1.1.40. The server only follows the number; the Android app 1.1.28 is unchanged. Update the Host and the Windows app together.

- **The keypad follows the NumLock of the keyboard in front of you.** With the NumLock light on it types digits, with it off it moves the cursor. The Host puts the desktop's NumLock where your keyboard's is when a keypad key arrives. It used to follow the desktop's NumLock, which could be the opposite of your keyboard's light.
- **The NumLock key acts on your own keyboard too.** Pressing it while connected switches the PC's NumLock.
- **Shift with a keypad key while NumLock is on does what it does on the PC.** It used to type a digit when the desktop's NumLock was on.
- **Host:** NumLock, Right Shift and Pause from a Windows app up to 1.1.37 arrive as themselves.

## [1.2.9](https://github.com/totblabs/Multitap/releases/tag/v1.2.9)

This is the Windows app 1.1.39. The server only follows the number; the Host 1.1.43 and the Android app 1.1.28 are unchanged.

- **The keypad follows the desktop's NumLock.** Pressing NumLock in a connection switches the desktop's NumLock, and the keypad types digits or moves the cursor as that says. 1.1.38 made it follow the NumLock of the keyboard in front of you, which cannot be switched while connected, so there was no way to turn the keypad back to digits.

## [1.2.8](https://github.com/totblabs/Multitap/releases/tag/v1.2.8)

This is the Windows app 1.1.38. The server only follows the number; the Host 1.1.43 and the Android app 1.1.28 are unchanged.

- **The keypad follows the NumLock of the keyboard in front of you.** It used to follow the desktop's NumLock. A PC with no keyboard attached starts with NumLock off, so on such a desktop the keypad worked as arrow keys instead of digits.
- **The NumLock key reaches the desktop.** Pressing it did not change the desktop's NumLock before.
- **Right Shift works.** It was not pressed in the desktop before.
- **The Pause key arrives as Pause.** It used to toggle the desktop's NumLock.

## [1.2.7](https://github.com/totblabs/Multitap/releases/tag/v1.2.7)

This is the server 1.2.7 and the Windows app 1.1.37. The Host 1.1.43 and the Android app 1.1.28 are unchanged.

- **The UDP buffer limit is raised so the server stops dropping a fast screen.** The relay asks for 4 MB socket buffers, and under Linux's stock limit it is granted 0.4 MB. What did not fit, the picture and the apps' requests alike, was dropped at the server: on one server 17,862 datagrams in 44 minutes, with a game freezing 0.6 s at a time. The install command and `multitap update`, `start` and `restart` now raise the limit (`net.core.rmem_max`, `net.core.wmem_max`) to 8 MB and keep it for the next boot. A larger value that is already set stays.
- **Run `sudo multitap restart` once after this update.** The update itself is carried out by the previous release's command, so the limit is raised from the next run on. Inside a CT the limit cannot be changed: it is raised on the Proxmox node, and the command says how.
- **The admin console says when the buffer is small.** Screen streaming over UDP in Server access shows "The UDP buffer is small" and how many datagrams were dropped.
- **The Windows app asks again sooner when a recovery request gets no answer.** When part of the picture was lost and the request to the Host was lost on its way, the app waited half a second before the next one. It now asks again after about 0.1 s. This applies to Hosts that answer with a recovery frame; with other Hosts nothing changes.

## [1.2.6](https://github.com/totblabs/Multitap/releases/tag/v1.2.6)

This is the Windows app 1.1.36. The server only follows the number; the Host 1.1.43 and the Android app 1.1.28 are unchanged.

- **The Windows app's quality settings let you choose the frame rate.** "Target frame rate" is Auto, 120, 90, 60 or 30. Auto goes up to the refresh rate of the monitor you view on; a number holds the stream at that rate at most. Before there were only 30 and 60, and 60 really meant "up to the monitor's rate", so on a fast monitor the only way to lower the frame rate was 30.
- **The current choice is shown.** On a connection running at 144 fps no button was lit and the quality mode read "Custom". Now Auto is lit and the mode reads "Work".

The Android app's quality panel keeps 30 and Auto.

## [1.2.5](https://github.com/totblabs/Multitap/releases/tag/v1.2.5)

This is Host 1.1.43. The server only follows the number; the Windows app 1.1.35 and the Android app 1.1.28 are unchanged.

- **The frame rate no longer goes up and down when the receiver cannot keep up.** When the receiving PC decoded slower than the stream's frame rate, the Host lowered the rate, raised it again ten seconds later, lowered it again when the receiver fell behind, and so on. Each round made pictures queue, and the mouse looked jerky. Now the rate goes up only when the receiver's own measure has room for it, and a rate that failed soon after it was tried is tried again more and more rarely (five minutes apart at most).

Found in the field record of a PC with integrated graphics only receiving a 144 fps stream (6.8 ms a picture; 144 → 90 → 120 → 90 …). A test built from those numbers stays at 90 fps. Not confirmed on a real connection yet.

## [1.2.4](https://github.com/totblabs/Multitap/releases/tag/v1.2.4)

This is Host 1.1.42. The server only follows the number; the Windows app 1.1.35 and the Android app 1.1.28 are unchanged.

- **On a narrow path the frame rate goes down and the picture goes on.** With a large picture at a high frame rate (2084×1340 at 144 fps, for one) the automatic rate could not go below 16 Mbps. On a path that carried less, the Host sent more than the path took, the picture froze for long and the stream left for the slow fallback. Now the frame rate steps down, to 30 at the lowest, and comes back two seconds after the path is wide again. A connection whose path is wide enough is not changed.
- **At a lower frame rate the whole allowed rate is used.** When a slow Host or a slow receiver lowered the frame rate, the encoder used only part of the rate (half of it at 30 instead of 60). Now the encoder is told the lower frame rate, and each picture is that much sharper.
- **Two monitors get the rate control of 1.2.2.** When the path suddenly carries less, the rate is set in one step from what actually arrived.

Simulation (the real sender, receiver and rate controller; 2084×1340 at 144 fps; the link at 8 Mbps for 40 s; five runs summed): 181 s frozen before, 6 s now; 369 s on the fallback before, none now. The encoder side was checked with the real x264, the Windows software encoder and NVIDIA (a Tesla P40). Not measured on a real connection yet. AMD and Intel GPU encoders cannot be told a frame rate and are as before. So are a path that does not carry 30 fps (about 3.4 Mbps for the picture above) and the frame rate of a two-monitor connection.

## [1.2.3](https://github.com/totblabs/Multitap/releases/tag/v1.2.3)

This is Host 1.1.40. The server only follows the number; the Windows app 1.1.35 and the Android app 1.1.28 are unchanged.

- **On NVIDIA GPU desktops a loss is no longer answered with a whole new picture.** At 120 fps and above every loss was, and on a GPU that keeps one reference frame (a Tesla P40, for one) at any frame rate. Now the Host keeps a few reference pictures that the Windows app holds as well, and sends only what changed since one of them. A loss up to 0.375 s back is repaired this way.

Checked on a Tesla P40 with the Windows app's own decoders (software and hardware): the side that lost frames shows the same picture as one that lost none. Not measured yet on another NVIDIA GPU or on a real lossy path. If the encoder does not do as asked, the Host sends a whole picture. The Android app, CPU encoding and AMD or Intel GPUs are as before.

## [1.2.2](https://github.com/totblabs/Multitap/releases/tag/v1.2.2)

This is Host 1.1.39. The server only follows the number; the Windows app 1.1.35 and the Android app 1.1.28 are unchanged.

- **The rate no longer stays low after a short dip in the path.** A dip of about 0.3 s could take the automatic rate to its lowest value and leave it there for minutes. Now the rate returns close to where it was within one to three seconds once the path is clear again.
- **A narrower path no longer sends the stream to the slow fallback for 30 s or more.** When the path suddenly carried less, the Host did not follow within a second and the picture froze for long. Now the Host sets the rate in one step from what actually arrived, and tries a new picture twice more before it leaves for the fallback.

Checked in a simulation that runs the real sender, receiver and rate controller together (a 144 fps game on a link that halves: 35.6 s frozen before, 1.7 s now). Not measured on a real path yet. The short freeze of the dip itself remains, and at 120 fps and above every loss is still answered with a whole new picture.

## [1.2.1](https://github.com/totblabs/Multitap/releases/tag/v1.2.1)

Android app 1.1.28 now requests the negotiated refresh rate as soon as a single-display stream starts or changes size. A new 120 fps connection could previously request 60 Hz from Android because the decoder still held the previous rate. The app also reapplies the current rate when Android recreates its display surface.

Update the server, then install Android app 1.1.28 from its download page. The corrected 120 Hz request was verified in a simulated connection. The resulting frame rate in a game on a phone still needs measurement.

## [1.2.0](https://github.com/totblabs/Multitap/releases/tag/v1.2.0)

Server 1.2.0, Windows app 1.1.35, Android app 1.1.27 and Host 1.1.38.

The development GPU negotiated 120 fps at 1080p. Sustained game presentation on a high-refresh monitor and playback on a physical Android device still need verification. The physical GPU desktop test covering USB, shared folders, disconnect, display restoration and Windows restart is also pending.

- **High-refresh streaming.** A new connection to a GPU desktop can use up to 240 fps when the viewing display, the decoder at the requested resolution and the Host encoder support it. With two displays, the slower display sets the limit. CPU encoding and connections with older components keep their 60 fps ceiling.
- **Dual monitors.** When one screen loses video packets, the Host can recover that screen independently. Each screen retries fast Windows capture if it becomes available again. Disconnecting also restores the display layout when the media connection closes during shutdown.
- **Android.** The app requests another recovery frame when the first reply is lost and requests a fresh set of lossless tiles when the picture falls out of sync. The Sharp setting allows the Host 15 seconds to return to full resolution after a temporary reduction.

## [1.1.58](https://github.com/totblabs/Multitap/releases/tag/v1.1.58)

### Host

- **The picture no longer turns small and slow after a size change.** Turning Android's Sharp on or off, or resizing a window, restarts the picture; when Windows' fast screen capture could not start at that moment, the Host kept a slow copy instead. It read the slowness as an overload, halved the picture and carried that size into the next picture, so Sharp was reported as unavailable. Now the fast capture is tried again at once and also while the picture runs, and a size cut made on the slow copy is not carried over. Two monitors try again at their start too.

### Server

- No change; the number follows the Host.

## [1.1.57](https://github.com/totblabs/Multitap/releases/tag/v1.1.57)

### Windows app and Host

- **Full-screen motion, such as a game, no longer freezes for 0.6 s at a time after a loss.** When the network loses data, the app names the last picture it has and the Host sends a recovery picture that follows from it. On a busy path that recovery picture could be lost as well, and the app then waited out the full half second before asking again. Now the app asks again as soon as it knows the recovery picture is lost, and the Host's repair limit no longer holds back a recovery picture. Either side alone helps; both together help most.

### Server

- The diagnostics record how many losses the Host answered and how many of those answers were key frames.

## [1.1.56](https://github.com/totblabs/Multitap/releases/tag/v1.1.56)

### Host

- **The automatic rate stops running into the network's limit.** Going over what the path carries loses data: every few seconds the rate rose to the limit and a picture was lost, and after 30 seconds it forgot the limit, climbed fast and overflowed, which froze the picture for 0.6 s several times in a row. The rate that lost is now remembered: it stays below it and tries above it only now and then, slowly. A better path is used again within about half a minute. This shows most in games and other full-screen motion.

### Server

- No change; the number follows the Host.

## [1.1.55](https://github.com/totblabs/Multitap/releases/tag/v1.1.55)

### Windows app and Host

- **A still screen becomes sharp again after the network loses data.** A loss could take lossless tiles with it; the app then stopped using tiles for the rest of the connection, and the Host, counting every tile as sent, never sent them again. Text looked fine, but small coloured labels and icons stayed smeared. Now the app asks for the tiles again and the Host sends them all anew. Both the app and the Host need this version.

### Server

- The diagnostics record how often a client asked for the tiles again.

## [1.1.54](https://github.com/totblabs/Multitap/releases/tag/v1.1.54)

### Host

- **Connecting with one monitor after using two no longer fails with "Couldn't change the number of monitors".** On a desktop with another display that is not Multitap's (a GPU's display, for example) and is switched off, Windows switched that display on by itself when one output was removed. The Host took it for a display it could not identify and undid the change, and every later one-monitor connection failed. - **Text no longer turns blurred while you type.** A small change (typing, a blinking caret, the mouse pointer, a ticked box) is sent as exact text tiles together with the video of the very moment it changed. Before, a part had to stay unchanged for 0.2 s to turn sharp, so it was blurred while typing.
- When a scroll or page switch stops, the screen turns sharp at once instead of after 0.2 s.
- Content that keeps moving (scrolling, a map) is video while it moves, as before. Works with the current Windows and Android apps.

### Server

- Unchanged; the number follows the Host.

## [1.1.38](https://github.com/totblabs/Multitap/releases/tag/v1.1.38)

### Windows app and Android app

- With several shared folders, one folder that stops answering (such as a hung network drive) no longer stalls the others or turns them "disconnected".

### Android app

- **Text on a still screen becomes sharp, as in the Windows app.** While the screen moves it is shown as video as before; when it stops, the changed parts are overlaid with exact text tiles. This works per screen with two monitors too.
- A phone that cannot draw this (no usable graphics, or a downscaled stream) shows the video alone as before.

### Server

- When the admin console turns on USB, shared folders or printers, the saved notice says that anyone connected now gets them after reconnecting. Turning them off applies at once, as before.

## [1.1.37](https://github.com/totblabs/Multitap/releases/tag/v1.1.37)

### Windows app

- A desktop card shows one moving mark while the desktop starts or shuts down: on the picture while previews are shown, on the status line when they are off. The main button no longer spins; it counts the elapsed time. The same sentence no longer appears on both the picture and the status line.
- The moment sharp text lands on a still screen is no longer recorded as a stall in the diagnostics.

### Host

- More diagnostics. The time from an input to the changed screen is recorded in two parts, the desktop's own drawing and the Host's capture, and the reasons the capture paused (window hidden, security prompt, display layout change) are recorded with their time. Streaming behaviour does not change.

### Server

- Accepts and stores the new diagnostics above.
- `multitap update` shows its steps (download, backup, release files, start, wait for an answer) as a progress bar and counts the seconds while it waits. On the Linux text console, such as the Proxmox console, which cannot draw Hangul or symbols, it uses English and ASCII marks.

## [1.1.2](https://github.com/totblabs/Multitap/releases/tag/v1.1.2)

### Server and admin console

- **Server access saves by itself.** On a Docker install, the page saves the addresses apps and Hosts use, the primary address, the trusted proxy IPs and public IP following. The server applies them by restarting itself, which ends open connections, and goes back to the previous settings if it cannot reach itself at the new address.
- **Public IP following** is a switch on the same page. While it is on, the server checks its public IP every 10 minutes and follows it.
- **The proxy is on this server**: one button adds a reverse proxy on the same machine to the trusted proxy IPs.
- **Restart server** is a button under Server info on a Docker install.
- **UDP screen streaming works on a default install** once UDP 18481 reaches the server. Apps and Hosts send to the address they connected on, and Server access shows whether UDP is in use.
- The memory limit of the server container can be raised with `MULTITAP_MEMORY_LIMIT` in `/opt/multitap/.env` (512 MB by default).
- The admin console says a Host request expires after 10 minutes, which is what the server does.

### Install command and `multitap`

- The installer's question about HTTP from outside now defaults to **No**.
- The installer keeps a log in `/var/log/multitap-install.log`, without the setup code. In a Proxmox CT with nesting off, it stops before installing anything and names the setting to change.
- `multitap status` shows whether the server answers, the last lines of its log and the free disk space, and warns when less than 2 GB is free.
- `multitap update` checks the new version through the container's own health check, so it works whatever address or port the server uses. It keeps the 3 most recent pre-update copies and removes server images older than the previous version.
- `multitap address` changes the same settings as Server access when the admin console cannot be reached: up to four HTTPS and four HTTP addresses, the primary address and the trusted proxies.

### Windows app

- Fixed: changing from one HTTP server address to another said the address was not saved and kept using the old one.
- With no server saved yet, the sign-in card opens on the server address form.

### Android app and Host

- No visible changes.

### Updating from 1.1.1

Run `sudo multitap update` on the server. If the server's only address is HTTPS, or its port is not 18480, run it twice: the 1.1.1 command checks the new version at `http://<server IP>:18480` and cannot see such a server, so the first run goes back to 1.1.1, but it installs the new command, and the second run succeeds.
