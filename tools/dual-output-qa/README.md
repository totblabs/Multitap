# Dual-output encoder and track QA

Standalone checks of the two-output (tracks-v1) media path with the product's
own code. Nothing here opens a screen capture, account, network, service,
registry key or display device.

## Encoder comparison (`MultitapDualOutputQa`)

Compares one wide encoder against two per-output encoders on exactly the same
NV12 source pixels, using the product `host::Encoder` (`apps/windows_host/src/
media.cpp`; the default backend of the Host build) and `FrameEncodePolicy`:

- one 3840×1080 encoder at 12 Mbps versus two concurrent 1920×1080 encoders at
  6 + 6 Mbps;
- both outputs moving; one moving and one static; both static;
- unconditional submission and the product `FrameEncodePolicy`;
- 30 and 60 fps, three seconds of media per sample, unpaced, repeated in
  alternating order to reduce ordering bias.

The deterministic fixtures and composite frames are generated and checked for
exact equality before measurement. Capture, cursor composition, NV12
conversion, transport and presentation are excluded; the policy's exact NV12
comparisons, snapshots, output PTS/IDR priming and one-second refresh are
included. `GetProcessTimes` gives user + kernel CPU across encoder threads,
reported as a **one-core equivalent** (CPU time / media time, which can exceed
100 %), not Task Manager's machine-wide percentage. The process runs below
normal priority with an affinity of up to four logical processors.

What it showed on a test VM: when one output is idle, two independently gated
encoders used about 43 % less CPU than one composite encoder, which cannot stop
encoding its idle half; with both outputs moving the two were within a few per
cent. Equal configured bitrate does not mean equal visual quality, and "two
tracks cost twice the CPU" and "one composite is always cheaper" are both
unsupported.

## Other targets

| Target | What it checks |
|---|---|
| `MultitapIdleWatchdogQa` | product `Encoder`, `FrameEncodePolicy` and the client's `RemoteDecoder` on a memory-only 640×360 scene at a wall-paced 30 fps: a single-byte change, a cursor-like patch and a final change followed by more than 15 s idle. Checks a usable IDR before drain, immediate output and decoding of each change (not waiting for the refresh), ordered submitted/encoded/decoded PTS, the visible patch and a maximum output gap of two seconds. Events are kept in memory and printed after the paced loop, so a slow console cannot become codec latency. |
| `MultitapTrackMediaQa` | the tracks-v1 packet writer and parser (header round trip, truncated, legacy and oversized packets) and per-track encoders feeding the client's `RemoteTrackDecoder` |
| `MultitapClientTrackEngineQa` | the client track engine on the CPU path (RGBA pixel buffers) and the GPU path (shared BGRA textures; WARP stands in for a GPU) |
| `MultitapClientTrackPresenterQa` | the track presenter on an owned hidden window against the CPU converter's pixels |
| `MultitapClientTrackBridgeQa` | (not built by default) a pipe adapter to the client's media owner and CPU decoder |

`MultitapClientTrackEngineQa` and `MultitapClientTrackBridgeQa` need the Flutter
C++ wrapper headers in `apps/windows_client/windows/flutter/ephemeral` (build
the Windows client once).

## Build and run

From the repository root, with the Visual Studio build tools in `.tools`:

```powershell
$cmake = '.tools/visualstudio-buildtools/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe'
& $cmake -S tools/dual-output-qa -B tools/dual-output-qa/build -G 'Visual Studio 17 2022' -A x64 "-DCMAKE_GENERATOR_INSTANCE=$($PWD.Path -replace '\\','/')/.tools/visualstudio-buildtools"
& $cmake --build tools/dual-output-qa/build --config Release --target MultitapDualOutputQa MultitapIdleWatchdogQa --parallel 2
& tools/dual-output-qa/build/Release/MultitapIdleWatchdogQa.exe
```

The encoder comparison takes `OUTPUT_DIR FPS REPEATS SECONDS`. Create a new
output directory; the executable refuses to overwrite stream files. It writes
JSONL to stdout and the generated Annex-B streams into that directory. Save
stdout as `native.jsonl` (Windows PowerShell 5's `Tee-Object` writes UTF-16;
the validator reads that as well as UTF-8):

```powershell
New-Item -ItemType Directory tools/dual-output-qa/NEW-RESULTS | Out-Null
& tools/dual-output-qa/build/Release/MultitapDualOutputQa.exe tools/dual-output-qa/NEW-RESULTS 30 3 3 | Tee-Object tools/dual-output-qa/NEW-RESULTS/native.jsonl
node tools/dual-output-qa/validate.mjs <ffmpeg.exe> <ffprobe.exe> tools/dual-output-qa/NEW-RESULTS
```

`validate.mjs` strictly decodes every repeat-zero stream with an FFmpeg build
you provide (software decoding; FFmpeg is QA-only and not part of the
product), checking geometry, pixel format, the full decoded frame count and the
generated byte counts, and records SHA-256 receipts of the decoder, binary and
inputs. Static samples have small CPU totals, so counter granularity and
run-to-run variation matter: compare ranges, not single values.
