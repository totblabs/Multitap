# 두 모니터 스트리밍 (모든 모니터 사용)

**모든 모니터 사용**은 원격 Windows의 소유 가상 출력 두 개(`0`, `1`)를 이 PC의 모니터 두 개에 하나씩 보여준다. 원격 쪽은 실제 확장 바탕화면이므로 창 최대화, 모니터 사이 창 이동, 마우스 이동이 원격 Windows의 두 화면 기준으로 동작한다. RDP의 다중 모니터 사용감을 참고했지만 전송은 Multitap 영상 스트리밍이다. 긴 영상 하나를 두 화면에 늘려 보여주는 방식이 아니다.

와이어 계약은 [remote-session-protocol.md의 independent outputs](remote-session-protocol.md#independent-outputs-tracks-v1), Host의 Windows 화면 처리는 [display-manager-v2.md](display-manager-v2.md)에 있다. 이 문서는 구조와 그 이유만 정리한다.

## 쓸 수 있는 조건

- 이 PC에 모니터가 정확히 두 개 있다. 주 모니터가 하나이고, 서로 겹치지 않고, 크기가 짝수여야 한다(`lib/data/local_display_layout.dart`). 세 개 이상이면 메뉴가 이유를 보여주고 이 모드를 막는다.
- Host가 `tracks-v1`과 출력별 크기 변경을 알린다.
- 세션 창은 연결할 때마다 원격 출력 개수를 화면 모드에 맞춘다. 창·전체 화면이면 1개, 모든 모니터면 2개다. 개수 변경은 스트림 밖의 별도 작업이다(`host.display.configure`).

## 구조

로그인 한 번, VM 권한 한 번으로 만든 **세션 하나** 안에 출력마다 영상 트랙을 하나씩 둔다. 엔진이나 프로세스를 두 벌 띄우거나 VM당 컨트롤러 제한을 풀지 않는다.

| 출력마다 따로 | 세션에서 함께 |
|---|---|
| 캡처, 인코더, 디코더, 화면 표시, 크기, epoch | 소리, 키보드·마우스 입력 소유권, 클립보드·장치 공유, 권한 회수, 연결 종료 |

- **출력 정체성:** 공개 ID `0`/`1`은 소유 출력의 connector 순서다. DISPLAY 번호, 장치 이름, 좌우 위치는 정체성으로 쓰지 않는다. `0`이 원격의 주 화면이다.
- **배치:** 클라이언트는 이 PC 두 모니터의 실제 픽셀 크기와 상대 위치를 그대로 요청한다. Host는 `1`을 `0`에 대해 같은 위치(왼쪽, 오른쪽, 위, 아래)에 둔다. 겹치는 요청은 거절한다.
- **표시:** 원격 창 하나가 두 모니터를 덮고, 같은 엔진이 출력마다 별도 디코더 텍스처를 해당 모니터 영역에 그린다. 가능하면 각 출력은 그 모니터를 구동하는 GPU에서 디코딩·변환한다(`windows/runner/remote_track_decoder.h`). 대화상자, 메뉴, 세션 툴바는 주 모니터 쪽에만 뜬다(`lib/ui/primary_region.dart`).
- **입력:** 포인터 입력은 어느 출력의 어느 epoch인지와 그 출력 안의 정규화 좌표를 함께 보낸다. 두 출력 사이를 오가도 입력 소유권은 하나다. 원격 화면 밖으로 포커스가 나가면 눌린 키와 버튼을 놓는다.
- **세대:** 크기 변경마다 topology epoch와 바뀐 트랙의 epoch가 올라간다. 이전 세대의 패킷과 지연된 요청은 새 세션이나 새 크기에 들어가지 못한다.

## 크기 변경과 실패

창 배치나 모니터 구성이 바뀌면 클라이언트가 두 출력의 새 크기와 위치를 한 번에 요청한다. Host는 두 출력의 크기를 SDK 재구성 한 번으로 바꾸고 Windows 배치와 출력별 캡처를 확인한 뒤 모든 트랙을 새 키프레임으로 다시 시작한다. 실패하면 저장한 화면 상태로 되돌리고 세션을 끝내거나, 마지막 수단으로 이전 크기를 그 자리에서 되살려 세션을 이어 간다(`stream.tracks.resize.restored`).

## CPU

출력을 나눈다고 인코딩 작업이 저절로 줄지는 않는다. 작업량은 픽셀 수, 변경 빈도, 코덱, FPS, 색 변환에 달려 있다. 이득은 한쪽만 움직일 때 나온다. 각 출력은 바뀌지 않은 프레임을 인코딩하지 않고 1초마다만 새로 고친다(`apps/windows_host/src/frame_encode_policy.hpp`). 합성 영상 하나는 움직이지 않는 절반도 계속 인코딩해야 한다.

`tools/dual-output-qa`에서 제품 인코더와 같은 정책으로 3840x1080 합성 하나(12 Mbps)와 1920x1080 두 개(각 6 Mbps)를 비교했다. 인코더와 정책만 잰 값이며 캡처, 전송, 디코딩, 표시는 포함하지 않는다.

| 장면 | 30 fps | 60 fps |
|---|---:|---:|
| 둘 다 움직임 | +2.0% | +2.6% |
| 한쪽만 움직임 | -42.7% | -42.7% |

(두 트랙의 CPU 시간 변화, 합성 하나 대비.) 지도를 두 화면에서 계속 움직이면 두 출력 모두 목표 FPS로 인코딩해야 하므로 이득이 없다. 사용자에게 보이는 FPS는 실제로 받은 프레임 수다.
